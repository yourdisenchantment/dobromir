## 1. Цель и рамки

Сайт фонда помощи детям с проблемами развития: лендинг с элементами
многостраничности — один вход (главная), с которого расходятся несколько
относительно самостоятельных разделов, каждый живёт по своим правилам
обновления (новости часто, брендбук почти никогда).

## 2. Как ты работаешь — и что это меняет в приоритетах

Ты один разработчик без большого опыта промышленной разработки и
полагаешься на AI-агентов. Это значит, что узкое место проекта — не
технологический выбор сам по себе (варианты для Astro/FastAPI +- одинаково
жизнеспособны), а то, насколько чётко зафиксированы решения, конвенции и их
причины, чтобы агент в новой сессии не переизобретал их заново и не тихо
отменял уже принятое.

В `cv` у тебя уже есть рабочий образец такого подхода — `AGENTS.md` как
единственный источник истины (`README`/`CLAUDE.md` — просто указатели на
него) с разделами Commands, Gotchas, Architecture, «Needs checking» (открытые
вопросы, которые нельзя тихо чинить) и «Settled» (принятые решения, которые
не надо переоткрывать). Дальше по документу я буду явно опираться на этот же
образец — подробнее в разделе 10.

## 4. Сквозные функции

- **Язык — только русский. Решено (2026-09-01), мультиязычность снята.**
  Причина: переводить контент некому. Посты приходят из VK на русском,
  машинный перевод текстов про детей с инвалидностью не годится, а
  переведённый интерфейс поверх русского контента даёт полупустую
  `/en/`-версию — это хуже, чем её отсутствие. Следствия шире, чем «не
  публикуем роут»: не подключается `astro i18n`, нет словарей и `t()` в
  компонентах, тексты пишутся в разметке напрямую; в `meta.json` поля
  становятся простыми строками вместо объектов `{ ru, en }` (раздел 6),
  то есть и контент-контракт, и обе схемы (pydantic/zod) проще. Цена
  обратного хода — переписать строки во всех компонентах; принято
  сознательно, зная эту цену.
- Четыре темы: светлая, тёмная, светлая контрастная, тёмная контрастная.
- Поддержка пользователей с проблемами со зрением: не только контрастные
  темы, но и семантическая вёрстка, управление с клавиатуры, читаемость
  скринридерами, масштабируемый текст без поломки layout — ориентир WCAG
  (международный стандарт доступности), не разовая «покраска» интерфейса.
- ~~Форма обратной связи по сайту~~ — убрана вместе с багрепортами,
  решено 2026-09-01, см. раздел 9.

## 5. Стек — принято

- **Фронтенд: Astro + bun.** У тебя уже есть рабочий опыт (`cv`), и это
  снимает основной открытый вопрос предыдущей версии плана. Смысл переносить
  оттуда: content collections + zod-схема для валидации структуры контента
  на этапе сборки, ESLint + Prettier + Husky + lint-staged + commitlint
  (Conventional Commits) как гигиена коммитов, `astro check` как
  единственная проверка типов, `eslint-plugin-jsx-a11y` как встроенный
  линт доступности — то есть требование «доступность» становится
  проверяемым в CI, а не только текстом в требованиях.
- **Все скрипты «под капотом»: Python + uv, один модуль `pipeline/`.**
  Уточнение по итогам обсуждения стека: раньше в этом разделе `vk-sync` и
  `content-tools` были на bun/TS ради общей zod-схемы с фронтендом — это
  явно пересмотрено. Правило теперь простое и без исключений: bun — только
  фронтенд, всё остальное — Python. В модуль входят:
  - перекачка контента из VK (`wall.get` для постов, `photos.getAlbums`
    — после ресёрча) — то, что раньше называлось `vk-sync`;
  - обработка контента (чистка метаданных, нормализация) — то, что
    раньше называлось `content-tools`;
  - отправка уведомлений в Telegram-бота (раздел 11).

  Модуль назывался `backend/`, пока в нём жил FastAPI. Веб-сервиса больше
  нет (раздел 9): не осталось ни одного эндпоинта, принимающего запросы,
  только скрипты по таймеру и исходящие уведомления. Имя `backend/` теперь
  вводило бы в заблуждение — отсюда `pipeline/`.

  Следствие: схему `meta.json` всё равно придётся держать в двух местах —
  pydantic на Python-стороне (пишет файлы), zod на Astro-стороне (читает
  файлы при сборке). Раньше это было доводом в пользу единого bun/TS-стека
  для контентных скриптов; сознательно принят обратный компромисс — один
  язык на весь «под капотом» проще для одного разработчика, чем общая
  схема ценой разбитого по языкам бэкенда. Расхождение схем — рабочий
  риск, а не забытый пункт: смотреть при правках формата `meta.json` в
  обе стороны.
- **Docker — пересмотрено, по умолчанию без него.** Раньше обоснование
  было «фиксировать версию `ffmpeg` надёжнее образом, чем через `apt`» +
  «лимит CPU/RAM на транскодирование». При вопросе «а точно нужен?»
  обе причины не выдержали проверки:
  - версию `ffmpeg` можно зафиксировать без Docker — пакетом вроде
    `imageio-ffmpeg`/`static-ffmpeg` (ставится через `uv` как обычная
    Python-зависимость, скачивает конкретную сборку бинарника при
    установке). Это решает именно то, из-за чего был нужен образ, без
    самого образа;
  - лимит CPU/RAM даёт не только Docker — systemd-юнит с `CPUQuota=`/
    `MemoryMax=` работает на тех же cgroups, что и Docker под капотом, без
    лишнего слоя.
  Что реально теряется без Docker: небольшая изоляция процесса (namespace
  вокруг `ffmpeg`, который трогает не полностью доверенный контент из
  VK) и чуть менее единообразная среда между ноутбуком и Selectel VM —
  митигируется тем, что `uv` уже жёстко фиксирует версии Python-пакетов
  (включая пин ffmpeg-бинарника через пакет выше), а держать одну и ту же
  версию Ubuntu на обеих машинах — разумная гигиена в любом случае.
  Взамен — на одну технологию меньше учить/обновлять, то есть прямое
  попадание в твой же принцип «меньше грузить себе мозг». Рекомендация:
  без Docker, обычный systemd (таймер на скрипты VK/обработки, `nginx` —
  пакетом из репозитория дистрибутива; постоянно висящих сервисов у нас
  нет, см. раздел 9). Откатить к Docker при необходимости легко — это не
  архитектурная развилка с высокой ценой пересмотра.
- **Про «ffmpeg или библиотеки Python» — вопрос снят как не совсем
  корректно поставленный.** Реального кодирования видео на чистом Python
  не существует: любая Python-библиотека для видео (`moviepy`, `PyAV`,
  `opencv-python`) в итоге вызывает те же нативные библиотеки кодеков
  (то же самое, из чего состоит сам `ffmpeg` — `libav*`), просто через
  разные обёртки. Выбор реально стоит между «дёргать `ffmpeg` как
  внешний процесс» (`subprocess`, прозрачно — команду можно скопировать и
  прогнать руками при отладке) и «слинковаться с той же библиотекой из
  Python» (`PyAV`). Рекомендация — `subprocess` + пин версии пакетом
  (см. выше): меньше абстракции, легче отлаживать, разница в
  производительности для нашего объёма несущественна. Для изображений
  отдельного вопроса нет — `Pillow` ставится как обычное pip/uv-колесо,
  без системных зависимостей.
- Репозиторий — приватный, **gitverse** (решено 2026-10-05, не GitHub). Следствие:
  `.github/` и Dependabot не используются; CI на gitverse остается открытым
  вопросом (раздел 14).

## 6. Контент-пайплайн: VK → сайт

Важное уточнение из последнего разговора: наполнение — не ручное
копирование папок, а автоматическая перекачка из VK-паблика фонда
(предположительно `vk.com/dobromir.crimea` — ссылка нашлась на старом
сайте, раздел 3; подтверди, если это не он). Это меняет, кто именно кладёт
файлы в `content-inbox/`, но не сам контент-контракт из предыдущей версии
плана — формат папки и `meta.json` остаётся внутренним интерфейсом между
этапами пайплайна, только раньше его писал ты руками, а теперь скрипт.
Ручное копирование остаётся как резервный путь — для того, чего в VK нет
или для правки неудачного авто-импорта, — но не основной сценарий.

Полная цепочка теперь в три этапа:

```
VK (источник)  →  vk-sync  →  content-inbox/  →  content-tools  →  content/  →  Astro build
```

`vk-sync` и `content-tools` — не отдельные модули, а функции внутри
единого Python-модуля `backend/` (решено на обсуждении стека, раздел 5);
названия оставляю как обозначение шагов пайплайна, а не как имена папок.
Официальный, легальный способ забирать посты — VK API (`wall.get` для
постов группы), не HTML-скрейпинг; ты уже писал похожее для пересылки
новостей в Telegram, логика подключения переносится. Нужен доступ: либо
токен сообщества (community access token, выдаёт админ группы в
настройках), либо токен standalone-приложения с правами `wall,photos`
(без `video` — вне MVP, раздел 8) — конкретный вариант зависит от того,
открыта ли группа, это стоит проверить в начале этапа 0.

Разбираю на два независимых источника внутри VK, раз ты сам разделил их по
сложности:

- **Посты со стены (→ «Новости»).** Понятная часть — то же самое ты уже
  делал для пересылки в Telegram. `wall.get` отдаёт текст и вложения (фото,
  ссылки, видео) одним вызовом; вложения типа `video` просто
  игнорируются на этапе синка — видео вне MVP (раздел 8), не нужно
  отдельно решать, что с ними делать. Смэппинг на наш контент-контракт:
  - заголовок — в посте VK его как отдельного поля нет, нужна эвристика
    (например, первая строка текста, или первые N символов, если строк
    нет) — стоит проверить на реальных постах группы, насколько это
    вообще осмысленно, прежде чем кодировать;
  - описание — весь текст поста;
  - теги — хэштеги из текста (`#тег`), если фонд ими пользуется, иначе
    список пустой;
  - закреп — `is_pinned` из ответа `wall.get` мэппится прямо на наше
    «закрепить» из раздела 4 — проверить точное имя поля в текущей версии
    API при реализации, за годы оно могло поменяться;
  - язык — вопрос снят: сайт только русский (раздел 4), поля языка в
    контракте нет вообще;
  - имя папки — `content-inbox/news/2026-08-10-vk12345/` (дата поста + ID
    поста из VK, не порядковый номер, который присваивал бы человек): ID
    поста уникален и стабилен, поэтому по нему легко понять, что пост уже
    импортирован, и не задублировать его при повторном запуске.
  - отслеживание правок и удалений — см. «Как устроен синк» ниже.

- **Фотоальбомы (→ «Галерея»).** Ты сам обозначил её как более сложную и
  требующую отдельного ресёрча — здесь специально не проектирую решение
  вперёд, чтобы не описывать несуществующий API-контракт. Известно только
  направление: `photos.getAlbums`/`photos.get` вместо `wall.get`. Видео из
  альбомов (`video.get`) — больше не часть ресёрча: видео вообще вне MVP
  (раздел 8), так что этот кусок неизвестности снят сам собой, а не
  решён. Что остаётся выяснить на этапе ресёрча: нужны ли более широкие
  права токена для закрытых альбомов, как ведёт себя пагинация на больших
  альбомах. До результата ресёрча этап с галереей в оценке (раздел 13)
  считаю неопределённым.

### Как устроен синк (обсуждено 2026-09-01)

**Объём зафиксирован: вся история паблика целиком** — все посты, все
альбомы, с самого начала. Из этого сразу следует, что долгая часть — не
тексты (сотни-тысячи постов это десятки запросов, то есть минуты), а
**медиа**: тысячи файлов по мегабайту-полтора. Дни уйдут туда, и всё, что
ниже про возобновляемость, в первую очередь про них.

**Три стадии, разделённые хранилищем, а не вызовом функции:**

1. `fetch` — единственное, что ходит в сеть. Забирает ответы VK и кладёт
   как есть, ничего не разбирая.
2. `parse` — читает сырое, раскладывает по полям. Сети не касается.
3. `export` — из разобранного делает то, что нужно сайту.

Смысл разделения — в том, что дорого и рискованно только первое (лимиты
VK, пагинация, обрывы). **Сырые ответы хранятся навсегда**, поэтому любая
переделка раскладки по полям — это перезапуск `parse` на локальных данных
за секунды, а не новый поход в VK. Пока контент-контракт не устоялся,
переделывать придётся много раз, и это главный аргумент за такое деление.

**Один цикл с приоритетом, а не два режима (идея пользователя, принята).**
Раньше здесь предполагались отдельно «полная выкачка истории» и отдельно
«ежедневный догон». Оказалось, это один цикл с правилом приоритета:

- есть записи новее самой новой забранной — берём их;
- нет — берём то, что старше самой старой забранной (движемся вглубь);
- нет ни того, ни другого — ничего не делаем.

Всё состояние выкачки — две отметки: самый новый забранный пост и самый
старый. Больше ничего, чтобы решить, куда двигаться на этом запуске.

**Форма — не вечный цикл с `sleep`, а запуск по таймеру,** который делает
одну порцию работы и выходит. Тогда «ждём» — это не состояние процесса, а
просто запуск, который ничего не нашёл. Восстановление после падений
достаётся бесплатно: упало на середине — таймер запустит снова, цикл
продолжится с сохранённой отметки. Согласуется с уже принятым «без
постоянно висящего демона» (раздел 11).

**Следствие для сроков: сайт полезен с первого запуска.** Свежие новости
появляются сразу, история дозаливается за ними следующие несколько дней.
Полная выкачка не блокирующий этап и не закладывается в оценку как
таковая.

**Что при реализации всплывёт — записано, чтобы не открывать заново:**

- *Смещение при выкачке вглубь.* `wall.get` листает по смещению от начала
  стены, а стена меняется: пока качаем четырёхсотый пост, наверху появился
  новый — всё сдвинулось на единицу, один пост проскочил. Порции надо
  брать с небольшим нахлёстом и стыковать по ID, а не доверять смещению.
  Удаления дают ту же проблему в другую сторону — там просто перезаберём
  лишнее, что безвредно при дедупликации по ID.
- *Закреплённый пост.* VK отдаёт его первым независимо от даты. Наивное
  «первый в выдаче — самый новый» на нём ломается: отметка «самый новый
  забранный» уедет на пост многолетней давности, и цикл решит, что новых
  нет. Баг получится тихий — не падение, а «перестало обновляться».
- *Правки старых постов.* Цикл ходит вперёд за новым и назад за старым, но
  никогда не возвращается к уже забранному. Пост, отредактированный два
  года спустя, останется у нас в старой версии. Это третий приоритет,
  самый низкий: изредка проходить по известному и сверять хэши. Нужен ли
  он вообще — зависит от того, правит ли центр старые публикации; вполне
  возможно, что нет, и тогда это осознанно не делается. **Открыто.**
- *Удаления.* VK не уведомляет — обнаруживается только сверкой списков,
  то есть тем же обходом, что и правки, и с той же оговоркой.

берёт то, что появилось в `content-inbox/`, и переносит в `content/`

пережатия видео/фото — там просто перенос текста и уже скачанных файлов).

**Именование и структура.** Один альбом — одна папка,

```
    IMG_2032.jpg
    .ready              # маркер «альбом полностью скопирован, можно брать»
```

`meta.json` — минимальный набор полей, без даты и номера (они уже есть в
имени папки — дублировать их в JSON означало бы завести два источника
истины об одном и том же и рано или поздно рассинхронизировать):

```json
{

  "description": "...",
  "tags": ["мероприятия"],
  "cover": "IMG_2031.jpg"
}
```

Поля — простые строки, а не объекты `{ ru, en }`: сайт одноязычный
(раздел 4).

Схема существует в двух копиях (см. раздел 5, почему так решено): pydantic
на Python-стороне валидирует `meta.json` перед тем, как его написать в
`content-inbox/`/перенести в `content/`; zod на Astro-стороне валидирует
его же при чтении на сборке. Оба места держать в курсе при любой правке
полей — синхронизация ручная, не техническая.

**Обработка** (Python, по таймеру раз в несколько минут — без постоянно
висящего демона, тот же аргумент, что и в первой версии плана):

1. валидация `meta.json` по схеме, проверка, что все файлы из `meta.json`
   (`cover` и т.п.) реально существуют в папке;
2. для фото — normalize: переименование в порядке сортировки (`01.jpg`,
   `02.jpg`, ...; заодно и приватность — родное имя файла с телефона вроде
   `IMG_2031.jpg` само по себе не несёт метаданных, но зачем оставлять
   рандомную последовательность), снятие EXIF/GPS с сохранением
   ориентации (её нужно «впечь» в пиксели поворотом кадра до чистки
   метаданных, иначе фото ляжет боком — см. Gotchas в будущем `AGENTS.md`).
   ~~**Скрипт не уменьшает разрешение**~~ (отменено 2026-10-25, см. разд. 8) — это принципиально, а не мелочь:
   `astro:assets` не умеет увеличивать изображения, поэтому файл в
   `content/` задаёт верхнюю границу качества для всего сайта, и он же
   уходит пользователю по кнопке «скачать» (раздел 8).
   Дальше **уменьшение и генерацию адаптивных размеров/WebP-AVIF для показа
   на сайте берёт на себя не скрипт, а встроенный image-pipeline Astro**
   (`astro:assets`, он и в `cv` косвенно используется) прямо во время
   сборки — он и так пересжимает картинку, что автоматически убирает
   метаданные ещё раз, без отдельного кода на это;
3. ~~для видео — сжатие через `ffmpeg`~~ — вне MVP (раздел 8), шаг не
   реализуется, пока видео не вернётся в объём;
4. перенос из `content-inbox/gallery/...` в `content/gallery/...`.

```
content/gallery/2026-08-10-01/
    meta.json
    01.jpg              # почищенный от метаданных, Astro сгенерирует
    02.jpg              # из него responsive-варианты при сборке
```

Как Astro читает `content/`, лежащую вне репозитория: `astro/loaders`
поддерживает `glob()` с произвольным `base`-путём — content collection
может смотреть на абсолютный путь на диске сервера (`/srv/dobromir/content`),
а не только внутрь `src/`. В `cv` `base` указывает внутрь репозитория
(`./src/data/cv`), механизм тот же самый, путь просто внешний. После того
как `content-tools` что-то поменял в `content/`, нужна пересборка
(`bun run build`) — тем же таймером следующим шагом после переноса файлов.

## 7. Темизация и доступность

- Технически — тот же паттерн, что уже проверен в `cv`: атрибут `data-theme`
  на `<html>`, значение в `localStorage`, применяется инлайн-скриптом до
  отрисовки (`pre-paint`), чтобы не было вспышки неправильной темы при
  загрузке. Для четырёх тем вместо одной меняется только набор значений и
  палитра CSS-переменных — сам механизм переносится без изменений.
- Контрастные темы — отдельно проверенные на соответствие WCAG AA/AAA по
  контрастности, а не «более тёмный тёмный».
- `eslint-plugin-jsx-a11y` (уже в стеке `cv`) переносится и сюда — это
  автоматическая проверка части требований по доступности прямо в CI.
- Для проблем со зрением, помимо тем: полная доступность с клавиатуры,
  `alt` у всех изображений (это же требование и к контент-контракту — поле
  `alt` в `meta.json` стоит сделать обязательным и проверяемым схемой),
  увеличение текста без горизонтального скролла, понятные
  фокус-индикаторы.
- Стоит добавить в CI автоматизированную проверку доступности уровня
  страницы (например, `axe-core`) — `eslint-plugin-jsx-a11y` ловит проблемы
  в разметке компонентов, но не всё (например, реальный контраст цветов
  после применения темы).

## 8. Медиа: фото, видео (отложено), стриминг и кэш

**Видео — сознательно вне MVP.** Пересмотрено: раньше был план на
самостоятельный хостинг с пережатием `ffmpeg`, теперь отказались —
«жирновато для сервера с сайтом», и отдельного запроса на видео по факту
не было. Формально стоит заметить: в самом первом описании задачи галерея
была заявлена как «фотографии и видео» (раздел 1) — так что это не то,
что видео нигде не звучало, а сознательное сужение объёма сейчас;
упоминаю на всякий случай, не как возражение. Следствие для стека:
весь разговор про `ffmpeg` (пин версии, subprocess vs PyAV, раздел 5)
пока не нужен на практике — оставил в разделе 5 как готовое решение про
запас, если видео вернётся в объём. Если видео всё же попадётся во
входящих постах VK (раздел 6) — по умолчанию просто не забирать вложения
типа video при синке, не пытаться встраивать и не пытаться показывать
ссылкой на VK — простое правило «нет видео» лучше, чем два разных
частичных решения. Если понадобится показывать хотя бы ссылку на видео в
самом VK (не хостить, просто дать посетителю попасть на пост) — это
дешёвая правка на потом, не архитектурная.

Дальше в разделе — то, что осталось актуальным, про фото:

**«Не нагружать устройство».** Кэширование заголовками `Cache-Control`:
для сгенерированных Astro ассетов (у них хэш в имени файла) можно смело
ставить `public, max-age=31536000, immutable` — имя изменится, если
изменится содержимое. Для файлов из `content/` («оригиналы» фото) хэша в
имени нет, там разумнее более короткий `max-age` + `ETag`, чтобы браузер
перепроверял, а не считал вечным.

**Показ и скачивание — решено (2026-09-01).** Развилка была между этим
разделом (Astro сам делает адаптивные варианты из одного файла) и идеей из
`idei-syrye.md` (скрипт кладёт два файла: лёгкое превью + оригинал). При
разборе выяснилось, что это одна и та же архитектура, если скачивание
ведёт на оригинал в полном разрешении; настоящая развилка была только в
том, что показывать в лайтбоксе. Принято:

- **всё, что видно на странице** — варианты от `astro:assets`: сетка
  превью и большой вид в лайтбоксе (ограничить по ширине, ~2000px хватает
  на любой экран), WebP/AVIF, `loading="lazy"`;
- ~~**кнопка «скачать»** — прямая ссылка на сырой файл из `content/`,
  который nginx и так отдаёт. Полное разрешение, исходный формат, никакой
  дополнительной обработки и никакого второго файла на диске.~~

**Пересмотрено 2026-10-25 (Павел):** кнопки «скачать» нет - сайт не для этого. Воркер при
приеме поста сам делает уменьшенную копию для показа (WebP), исходник не хранится;
`astro:assets` для фото новостей не нужен. Размеры - в задаче на фото (BACKLOG).

Почему не отдавать оригинал прямо в лайтбокс: фото из VK — это обычно
4000×3000 и 4–6 МБ, а на экране оно всё равно ужимается до ширины окна.
Пользователь скачал бы мегабайты ради той же картинки, что и в 2000px-WebP
на ~300 КБ — прямо против принципа «не грузить трафиком ни пользователя,
ни сервер». Кому нужен реальный оригинал, тот жмёт «скачать», и это
осознанное действие, а не побочный эффект клика по превьюшке.

Отдельный шаг «сгенерировать превью на несколько килобайт» из
`idei-syrye.md` не нужен: самый узкий `width` из Astro плюс `lazy` дают то
же самое нативно.

**Что проверить до того, как это станет кодом.** `content/` лежит вне
репозитория (`/srv/dobromir/content`, раздел 6), а Astro обрабатывает
изображения, только если может разрешить их как ассеты — через `image()` в
схеме коллекции. С glob-loader'ом и абсолютным внешним `base` это в
принципе должно работать, но у Vite есть ограничения на файлы вне корня
проекта, и на дев-ноутбуке этой папки просто нет. Проверяется за полчаса
на трёх файлах, и проверить надо до галереи, а не в середине. Запасные
ходы, если не заработает: симлинк `content/` внутрь проекта, либо отказ от
Astro-обработки в пользу готовых размеров из скрипта.

Второе, поменьше: сборка на 2 vCPU прогоняет `sharp` по всем фото. Astro
кэширует обработанные картинки между сборками, так что регулярная
пересборка после синка дешёвая, а первая по большому архиву альбомов будет
заметной — не проблема, просто не пугаться.

```
dobromir/

├─ pipeline/            # Python + uv — всё, что общается с VK (раздел 5)
│  ├─ pyproject.toml
│  ├─ src/pipeline/
│  │  ├─ vk/            # клиент: токен, лимитер, ретраи, пагинация
│  │  ├─ fetch/         # стадия 1 — сырые ответы в хранилище
│  │  ├─ parse/         # стадия 2 — сырое → нормализованные записи
│  │  ├─ export/        # стадия 3 — записи → то, что читает сайт
│  │  ├─ store/         # схема БД, доступ, миграции
│  │  ├─ media/         # скачивание файлов, чистка метаданных
│  │  ├─ notify/        # телеграм

│  └─ deploy.sh
│

```

Три уровня `pipeline/` — это не любовь к папкам, а прямое отражение стадий
синка из раздела 6: `fetch`/`parse`/`export` разделены, потому что только
первая стадия ходит в сеть и только её больно перезапускать.

**Данные в репозитории не лежат вообще:**

```
$DOBROMIR_DATA/          # на ноутбуке одно, на сервере /srv/dobromir
├─ raw/                  # сырые ответы VK
├─ state.sqlite          # что забрано, что изменилось, где остановились
├─ media/                # скачанные файлы
└─ content/              # то, что читает Astro на сборке
```

Один путь в переменной окружения, одинаковая раскладка на ноутбуке и на
сервере — разница между машинами сводится к одной переменной, а не к
другому коду. Прямо обслуживает принцип «сначала всё гонять локально» из
`idei-syrye.md`.

**Статус: обсуждено, не финализировано** (2026-09-01) — структура выше
проговорена, но за работу пользователь ещё не брался, так что имена и
границы папок могут поехать при первом же соприкосновении с кодом.
Зафиксировано, чтобы не собирать заново, а не как окончательное решение.

Два модуля вместо прежних четырёх — прямое следствие «bun только для
фронтенда, всё остальное — Python» (раздел 5). Общего пакета схем между
ними больше нет: `meta.json` валидируется дважды, отдельно с каждой
стороны (тоже раздел 5).

**CI-гейты**, раздельно по модулю:

- frontend: `bun install --frozen-lockfile` → `eslint` → `prettier
  --check` → `astro check` → `astro build` — тот же порядок, что уже
  обкатан в `cv`;
- pipeline: `ruff` → `mypy` → `pytest` (VK-синк и обработка контента —
  единственное, что там теперь есть, раздел 9);
- оба модуля: `commitlint` на Conventional Commits, защита `main` от прямых
  пушей (мердж только через merge request, CI обязателен зелёным).

**Гигиена репозитория — сделать до первого коммита, а не после.** Репозиторий
приватный на gitverse (решено раньше). Три вещи, которые потом чинятся
мучительно:

- **токен VK не попадает в репозиторий ни в каком виде** — ни в конфиге, ни
  в примере, ни в тесте. Переменная окружения, на сервере — через
  `EnvironmentFile` у systemd-юнита. Приватность репозитория этого не
  заменяет: она защищает от чужих, а не от того, что секрет навсегда
  останется в истории коммитов;
- **`.gitignore` до первого коммита**: данные (`$DOBROMIR_DATA`), `.env`,
  `dist/`, `node_modules/`, `.venv/`. Один неаккуратный `git add .` в
  проекте с медиафайлами разбирается долго;
- **проверить, что на gitverse с CI и в каком виде.** Гейты выше — это
  единственное, что в модели работы «через агентов» страхует от тихой
  поломки уже работающего (раздел 2). Если CI там нет или он неудобный —
  это не повод менять хостинг, но повод заранее решить, чем гейты
  заменить, хотя бы pre-commit хуками локально. **Открыто.**

**Деплой — под твою модель `git pull`.** В отличие от `cv` (там деплой —
встроенный механизм GitHub Pages/Cloudflare Pages, привязанный к их
хостингу), здесь свой сервер на Selectel, поэтому нужен явный скрипт,
например `infra/deploy.sh`. Без Docker (раздел 5) шаги — обновить код,
пересобрать фронтенд, обновить Python-окружение и перезапустить systemd-юниты:

```sh
git pull --ff-only
(cd frontend && bun install --frozen-lockfile && bun run build)
(cd pipeline && uv sync --frozen)
sudo systemctl reload nginx   # если менялся конфиг nginx
```

Перезапускать нечего: постоянно работающего сервиса у нас нет (раздел 9),
а таймер подхватит новый код скриптов на следующем запуске.

`nginx` отдаёт собранный `frontend/dist/` и `content/` напрямую — и больше
ничего. Проксировать нечего: динамических запросов у сайта нет (раздел 9).
VK-синк и обработка контента — не веб-сервис, а `dobromir-content.timer` →
`dobromir-content.service` (`Type=oneshot`), с `CPUQuota=`/`MemoryMax=` в
юните вместо контейнерных лимитов (раздел 5).

Запуск деплоя — вручную по SSH, что полностью соответствует твоей
формулировке; при желании позже можно добавить лёгкий webhook-приёмник на
пуш в `main`, но это не обязательно на старте.

**Домен и TLS.** `dobromir.ru` — A-запись (и AAAA, если у VM будет IPv6) на
публичный IP сервера в Selectel. TLS — `certbot`/Let's Encrypt, автопродление
по таймеру. Стоит сразу выбрать канонический вариант (`dobromir.ru` без
`www` или наоборот) и сделать 301-редирект с другого — иначе задваивается
SEO и куки/кэш ведут себя непредсказуемо между двумя хостами одного сайта.

**Хостинг (Selectel).** Заявленный трафик нишевый, без ожидаемых пиков —
значит один облачный сервер минимальной конфигурации (например, 2 vCPU / 2–4
ГБ RAM) без Docker закрывает потребность с запасом; CDN и
объектное хранилище можно не подключать на старте, добавить позже, если
объём медиа или трафик вырастут. Это сознательно менее «на вырост», чем в
первой версии плана — там я закладывал CDN/S3 без вводных по трафику,
теперь вводная есть.

**Резервное копирование.** Ежедневный снапшот `content/` (уже
обработанного, не `content-inbox/`) на второй диск/регион — код и так в git,
а безвозвратно потерять медиа и тексты новостей обиднее всего. Отдельный
плюс от того, что VK — источник истины (раздел 6): новости в принципе
можно перекачать заново из VK, если `content/` потеряется, — это не
заменяет резервные копии (перекачка небыстрая и не восстановит то, что
успели удалить в самом VK), но снижает цену ошибки.

**Логи и уведомления об ошибках.** Раз цель — минимальное ручное участие
(«поиск ошибок, анализ логов, корректировки», как ты сформулировал), это
предполагает, что ошибки сами долетают до тебя, а не ждут, пока ты зайдёшь
проверить логи. Предлагаю: скрипты VK-синка и обработки контента (раздел 5)
на каждый запуск пишут структурированную запись в лог (сколько постов/альбомов забрали,
сколько создали, сколько пропустили, что упало) и при любой ошибке шлют
короткое сообщение в телеграм-бот. Бот теперь один и только на исходящие
(раздел 9): health-checking — что синк сделал, что упало. Лог на диске
остаётся источником для разбора, уведомление — просто триггер «зайди
посмотреть».

## 12. Организационный флаг — не архитектурный

Сайт публикует фото детей с инвалидностью — чувствительные персональные
данные несовершеннолетних (видео сейчас вне MVP, раздел 8, но принцип тот
же на будущее). Проект официальный, заказан напрямую директором центра
Ларисой Семёновной Шепитько (раздел 14) — это снимает вопрос «к кому
вообще обращаться», но не сам вопрос согласия: то, что фонд сам
опубликовал материал у себя в VK-паблике, не равно согласию на
автоматическое зеркалирование на отдельный сайт бессрочно и без контроля
над тем, что там окажется. Разговор с директором про это отдельно —
нужно ли явное согласие на такое зеркалирование и как его фиксировать —
ещё не проведён, это не техническое решение. Технически контент-контракт
можно дополнить обязательным полем «согласие получено: true/false» (или
сделать публикацию per-item выключаемой вручную), а чистка EXIF с
геолокацией (раздел 6) — прямая техническая мера защиты, её имеет смысл
сделать в любом случае, независимо от организационного решения.

## 13. Укрупнённая оценка по этапам

Проект petproject-темпа — жёсткого дедлайна нет, поэтому «недели» ниже
скорее про объём работы, чем про календарь: ориентир — темп ~15–20 часов в
неделю, но можно растягивать без потери качества плана, в отличие от
проекта с внешним сроком.

**Определение MVP уточнено (2026-09-01):** это полностью рабочий сайт, в
котором остаётся править стили и макеты, а весь функционал загрузки и
отображения данных работает. Критерий по функциональности, а не по списку
разделов. Прямое следствие: Галерея входит в объём, значит VK-спайк —
блокирующий этап, а не опциональный. **Решено делать его первым**, до
контента и контрактов: схему проще проектировать под то, что VK реально
отдаёт, чем переделывать её потом.

| Этап | Содержание | Срок |
|---|---|---|
| 0. VK-спайк | Доступ к `vk.com/dobromir.crimea` через API, `wall.get` на реальных постах (работает ли эвристика заголовка, пользуются ли хэштегами), `photos.getAlbums`/`photos.get` для Галереи — права токена, пагинация, что реально лежит в альбомах | 3–5 дней на посты, альбомы — неопределённо, станет понятнее по итогам |
| 1. Контракты и скелет | Контент-контракт (`meta.json`-схемы) под то, что реально отдаёт VK, скелет монорепозитория, `AGENTS.md`, CI-гейты | 1 неделя |
| 2. Каркас | Frontend-скелет на Astro (layout, светлая/тёмная темы, `sections.ts`), `vk-sync` для постов → «Новости», разделы «Главная», «Новости», «Контакты» | 2–3 недели |
| 3. Остальные разделы | Программы, Сотрудники, О нас, Достижения, Галерея — по разделу 3 | 3–4 недели |
| 4. Медиа-пайплайн | Обработка фото (впекание ориентации, чистка EXIF/GPS), Astro-варианты, скачивание оригинала (раздел 8) | 1 неделя |
| 5. Доступность и темы | Контрастные темы, `axe-core` в CI | 1–2 недели |
| 6. Прод-контур | Деплой-скрипт на Selectel, TLS, бэкапы, логи/алерты, документация процесса | 1–2 недели |

Итого **~10–14 недель** в темпе 15–20 ч/неделю (это ~145–280 часов), при
условии что спайк не принесёт сюрпризов по альбомам. Сумма строк таблицы
выше - 9.6 недели по нижним границам и 14 по верхним; прежняя запись
«~9–12» (2026-09-01) занижала верхнюю границу, исправлено 2026-10-06. Все
равно меньше, чем в прошлой версии, при том что объем вырос (Галерея теперь
внутри MVP) - за счет снятых мультиязычности (раздел 4) и всего бэкенда с
формой (раздел 9).

Осталось открытым:

- **База и её роль — главная незакрытая развилка (появилась 2026-09-01).**
  Договорились, что скраперу нужна база (SQLite): дедупликация по ID,
  отслеживание правок и удалений, отметки выкачки, архив сырых ответов
  (раздел 6). Не решено другое — **это внутренняя кухня пайплайна или
  источник, из которого сайт читает при каждом запросе.**
  - вариант А: база внутренняя, `export` материализует файлы, сайт
    статичный — всё, что решено сегодня (разделы 8, 9), остаётся в силе;
  - вариант Б: FastAPI отдаёт базу сайту в рантайме — сайт перестаёт быть
    статичным, возвращается входящий эндпоинт (отменяет раздел 9), и
    **разваливается решение по фото**: `astro:assets` работает на сборке по
    файлам, а не по данным из API, значит адаптивные варианты снова надо
    делать самому (то есть возвращается отменённый «превью + оригинал
    скриптом», раздел 8).
  Рекомендация — А; Б покупает только «контент появляется без пересборки»,
  что при ~100 посетителях в день и новостях пару раз в неделю не стоит
  своей цены. Решать не срочно: стадии `fetch`/`parse` одинаковы в обоих
  вариантах, а это основной объём работы. Пока развилка открыта, папку
  `server/` в репозитории **не создавать** — пустой каталог читается как
  «тут что-то должно быть», и агент в новой сессии начнёт его заполнять.
- Разделы сайта — черновик в разделе 3 по старому сайту, ещё не
  подтверждён/не поправлен.
- **Содержание страниц не описано вообще** — самая большая дыра в
  спецификации на сегодня. Механизм решён (`sections.ts`, один
  упорядоченный массив описывает и состав блоков, и пункты шапки,
  `idei-syrye.md`), но нигде не сказано, какие блоки на главной, что
  показывает «Программы», какие поля у карточки сотрудника (кроме
  черновика), что содержательно такое «Достижения». Верстать по текущим
  документам нельзя — это не про дизайн, а про то, чего на страницах ещё
  нет.
- Точная схема `meta.json` для остальных типов контента — для галереи и
  черновика «сотрудников» (раздел 6/`idei-syrye.md`) есть пример, для
  новостей/программ ещё нет. Проектируется после спайка (этап 0), под то,
  что VK реально отдаёт.
- Обрабатывает ли `astro:assets` изображения по внешнему пути
  (`/srv/dobromir/content`, вне корня проекта) — проверить до Галереи,
  запасные ходы описаны в разделе 8.
- Организационный вопрос о согласии на публикацию фото детей (раздел 12) —
  контакт для разговора есть (см. первый пункт), сам разговор не проведён.
  Единственное, что может отменить целый раздел уже после того, как он
  написан.
- Структура проекта (раздел 11) — проговорена, но не проверена кодом;
  имена и границы папок могут поехать при первом соприкосновении.
- Правки старых постов — нужен ли третий, низкоприоритетный проход по уже
  забранному (раздел 6). Зависит от того, правит ли центр старые
  публикации.
- CI на gitverse — есть ли, в каком виде, чем заменять, если неудобно
  (раздел 11).
- Конкретная конфигурация Selectel VM — минимальный тариф выглядит
  достаточным, но стоит подтвердить после того, как появится оценка объёма
  медиа. Оценка объёма медиа теперь ожидается от спайка: вся история
  паблика — это тысячи файлов, и место под них надо считать заранее.
