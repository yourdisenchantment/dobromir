- Принятая схема проверена на практике: Node 24.15.0 ставится и запускается из cron, Astro собирается на хостинге.
- Жесткие запреты Beget: демоны запрещены правилами (значит, никакого uvicorn и Long Poll), лимит 80 CP в сутки.

## 4. Правила и ограничения Beget (документ "Правила использования", п. номера по https://beget.com/ru/pravila)

- [док] п. 6, 22.4: **запрещено размещать приложения, работающие в фоновом режиме (демоны)**. Следствие: нельзя держать uvicorn/FastAPI как сервер и нельзя Long Poll VK.
- [док] п. 22.1: лимит 80 CP в сутки на тарифе Blog. п. 23: можно докупить не более 200 CP.
- [док] п. 22.4: до 30 одновременных процессов на домен, 6 ГБ RAM на процесс, 32 открытых файла на процесс, до 5 000 000 файлов на аккаунте. Реальный `ulimit -n` в оболочке 1024, так что лимит файлов для сборки Astro - риск, а не подтвержденная проблема.
- [док] Python на shared официально идет через Passenger (WSGI), ASGI не поддерживается. Для нашей схемы веб-приложение не нужно.
- [док] Node.js на shared запускается только внутри Docker-окружения по официальной статье Beget. Практика: на этом сервере Node из `~/opt/node` запускается и из cron на хосте (проверено).
- [док] Из-за изоляции аккаунтов на основе POSIX ACL, программы в `.local` по умолчанию недоступны веб-серверу, нужно открывать общий доступ через файловый менеджер. Вывод [гипотеза]: **все, что должен отдавать веб-сервер (релизы, медиа), держать внутри папки сайта** `~/a978879k.beget.tech`, а не в произвольных каталогах домашней папки.
- [док] п. 21: Beget вправе принудительно менять пароль аккаунта и включать 2FA. Автоматику на пароле не строить, использовать SSH-ключи.
- [док] п. 5: запрещена обработка персональных данных третьих лиц без согласия. Новости из публичной группы центра обычно допустимы, но фото детей согласовывать с центром.
- [док] Cron: интервалы вплоть до `*/x`, вывод может уходить на email, есть вкладка "Запустить скрипт" для разовой проверки. Cron-задания в панели: типы "Произвольная команда", "Bash-скрипт" и др.
- [док] В официальных статьях Beget используются `git clone`, `pip --user`, `python3 -m venv`, символические ссылки (`ln -s public_html public`) и `.htaccess`.

## 5. Выводы по технологиям

- **FastAPI как HTTP-сервер на Beget не используется.** Код бэкенда (слой SQLite, парсинг, модели) переиспользуется воркером как библиотека.
- **Long Poll VK не используется** (демон запрещен). Вместо него опрос раз в 2 часа: `wall.get` окна последних постов при каждом запуске плюс раз в сутки полная сверка всех сохраненных постов через `wall.getById`. Бонус: так отслеживаются **правки и удаления** постов, чего Long Poll с событием "добавление" не делал бы. Задержка появления новости и изменений до ~2 часов, владелец сайта это принял.
- **Сборка Astro на самом хостинге:** Node 24 в `~/opt/node`, менеджер пакетов npm. Bun Beget не документирует (ядро 5.10, технически, вероятно, запустится, [гипотеза]) - на сервере не использовать. Если локально используется Bun, держать lock-файл npm (`package-lock.json`) как источник истины для сервера, или перейти на npm полностью, чтобы lock-файлы не расходились.
- **Переменные окружения для сборки:** `PATH=$HOME/opt/node/bin:$PATH`, `ASTRO_TELEMETRY_DISABLED=1`.
- Python для воркера: 3.10.12 хоста. Зависимости минимальные, версии зафиксированы, виртуальное окружение (`python3 -m venv`) [гипотеза, проверить на хосте, в Docker работает по статье].

## 6. Целевая архитектура

```text
cron (раз в 2 часа, например "17 */2 * * *", панель Beget -> CronTab)
    -> deploy/run-worker.sh          (задает PATH, переменные, пишет лог)
    -> worker (Python 3.10)
        1. блокировка от параллельного запуска (fcntl-lock, не flock)
        2. VK wall.get: окно последних постов группы (по умолчанию 50)
           раз в сутки (первый запуск после 03:00 по Europe/Simferopol):
           полная сверка всех сохраненных постов через wall.getById
        3. сравнение с SQLite: новые, измененные (по хэшу отображаемого
           содержимого), удаленные (пометка deleted_at, физически не удалять);
           защита от массового ложного удаления (раздел 9)
        4. скачивание новых картинок в папку медиа внутри папки сайта
        5. если изменений нет -> выход, обновить status.json
        6. если изменения есть и суточный лимит сборок не исчерпан:
              экспорт данных для Astro (JSON)
              сборка Astro в releases/<время>/
              проверки целостности релиза
              атомарное переключение ссылки public_html
              чистка старых релизов (оставить 5)
        7. если лимит сборок исчерпан -> пометить "ожидает сборки" в status.json
        8. при любой ошибке: код выхода не 0 (cron пришлет письмо), статус в status.json
```

Сайт всегда статичный: nginx отдает готовые файлы. Если воркер, VK или сборка упали, остается предыдущий релиз.

Правила:
- В git не попадают: `.env`, `*.sqlite`, `node_modules`, `dist`, медиа.
- Деплой: `git pull` на сервере по read-only deploy-ключу, затем `deploy/deploy.sh`. CI GitVerse для проверок (тесты, линтер, SEO-проверки) - желательно, доступность и синтаксис не проверялись.
- Данные и конфиги сервера лежат в `deploy/`, чтобы окружение можно было восстановить.
- **Роль GitVerse: только удаленный git для кода.** Базы с новостями, SQLite, медиа и секретов в нем нет и не будет. Публикации через CI на Cloudflare Pages или GitHub Pages не планируется: сайт собирается и публикуется на самом хостинге Beget воркером.
- Поток кода: разработчик пушит в GitVerse со своего устройства, на сервере `git fetch` и `deploy/deploy.sh <тег>`. Автоматический `git pull` по cron не делать: непроверенный код не должен менять боевой сайт без присмотра. На время отсутствия разработчика сервер закреплен на теге релиза (например `v1.0.0`).
- Все, что генерирует воркер (экспорт новостей, релизы, медиа, статус), лежит вне клона репозитория или в `.gitignore`, чтобы `git pull` не конфликтовал.
- Первый тест до начала реализации: доступ с хостинга к `gitverse.ru` и способ аутентификации (SSH deploy-ключ или HTTPS с токеном только на чтение). Поддержка deploy-ключей в GitVerse не проверялась.

## 9. Требования к воркеру

1. Идемпотентность: повторный запуск без новых данных ничего не делает и не собирает сайт.
2. Блокировка от параллельных запусков через lock-файл (fcntl), чтобы не пересекались запуски cron.
3. Опрос VK при каждом запуске: `wall.get` окна последних постов (параметр `VK_WINDOW`, по умолчанию 50; учесть закрепленный пост, он может стоять вне хронологии). Для каждого поста считается хэш только того содержимого, которое показывается на сайте: текст, состав вложений, идентификаторы медиа, поле `edited` (время последней правки, если API его возвращает [гипотеза]). Счетчики лайков, просмотров, комментариев в хэш не входят, иначе сайт пересобирался бы без причины.
4. Сборка **только при наличии изменений** (новый, измененный или удаленный пост). Несколько изменений за один запуск дают одну сборку. Параметр `MAX_BUILDS_PER_DAY` (по умолчанию 4) - страховка от всплеска или бага, а не рабочее ограничение. Если лимит исчерпан, изменения остаются в очереди (статус "pending") и собираются первым запуском после смены суток (Europe/Simferopol).
5. Картинки скачиваются один раз при получении поста, URL VK не хранить как постоянные.
6. Текст постов экранировать, разметку VK (`[club123|текст]`, хэштеги, ссылки) преобразовывать отдельно, чтобы не было XSS.
7. Сборка Astro в новую папку, проверки релиза (есть `index.html`, `sitemap`, число страниц не упало ниже предыдущего минус допуск), только после этого переключение ссылки.
8. Ошибки: ненулевой код выхода, понятное сообщение в stderr (уйдет письмом из CronTab), запись в `status.json` и лог с ротацией.
9. `status.json`: время последнего успешного опроса, время последней сборки, число постов, ошибки, число сборок за сутки, признак "pending".
10. Ошибка авторизации VK (токен): отдельное, понятное сообщение в письме.
11. Секреты берутся из `.env` в `~/dobromir-data/`, не из репозитория.
12. Правки: пост найден в базе, хэш изменился - запись обновляется, `edited_at` сохраняется, запускается сборка. Новые или замененные картинки скачиваются, ненужные медиа удаляются через 30 дней после последнего использования (запас на откат).
13. Удаления: пост помечается `deleted_at` (мягкое удаление), в экспорт для Astro не попадает, страница новости исчезает из сборки (404), из sitemap и RSS убирается. Признак удаления: пост есть в базе, его дата попадает в охваченный окном диапазон (закрепленный пост исключить из этого правила), а в ответе VK его нет; для постов старше окна - ответ `wall.getById` без этого поста. Если пост снова появится в VK, пометка снимается.
14. **Защита от ложных удалений:** ошибка VK, пустой ответ, ошибка токена или временный сбой не считаются удалением. Если за один запуск к удалению помечается больше `max(3, 20% сохраненных постов)`, изменение не применяется, запуск завершается ошибкой с понятным сообщением (письмо cron) и записью в `status.json`.
15. Даты на сайте только **абсолютные**: формат "12 октября 2026" (локаль ru), без "3 дня назад". Время в разметке `<time datetime="2026-10-12T14:30:00+03:00">` в часовом поясе Europe/Simferopol, фиксированном в сборке (пост, опубликованный в 23:30, не должен менять дату). Если пост правили, показывать "Обновлено 14 октября 2026" (только когда дата правки отличается от даты публикации). Лента новостей сортируется по дате публикации.
16. Тесты на разбор постов VK (форматы, вложения, репосты), на логику лимита сборок и на атомарность переключения; отдельно на: правку текста (сборка есть), изменение только счетчиков лайков (сборки нет), удаление, восстановление удаленного поста, защиту от массового удаления, ошибку VK (не удаление), форматирование абсолютной даты на границе суток.

## 10. Сборка и деплой: детали

- `astro.config.mjs`: `outDir: process.env.ASTRO_OUT_DIR ?? './dist'`; `trailingSlash` согласовать со старыми адресами (у WordPress адреса оканчивались на слэш); `site` из переменной.
- Данные для страниц новостей Astro читает из JSON, путь передается переменной (`NEWS_JSON`).
- Установка зависимостей на сервере один раз (`npm ci`), `node_modules` остается на сервере. Повторная установка только при изменении lock-файла (деплой).
- В cron-скриптах `PATH` задавать явно. Cron-задание в панели CronTab (пример): `cd ~/dobromir && ./deploy/run-worker.sh`, расписание раз в 2 часа, например `17 */2 * * *` (минута не 0, чтобы не попадать на пик; при необходимости можно реже, например `17 */3 * * *`). Суточная полная сверка постов выполняется тем же заданием, отдельного cron не нужно.
- Откат: переключить ссылку на предыдущий релиз; релизы хранятся (5 последних).
- Бэкап SQLite отдельным cron-заданием через `sqlite3 .backup` (раз в сутки), хранить несколько копий внутри аккаунта; автобэкапы Beget - дополнительная защита.

## 11. SEO и читаемость краулерами (требования к фронтенду)

- Весь контент в готовом HTML, без загрузки новостей на клиенте через fetch. Режим SSR не нужен.
- `<html lang="ru">`, уникальные `title` и `meta description`, `canonical`, один `h1`, порядок заголовков, семантические теги, `alt`, `width`/`height` у картинок (оптимизация через `astro:assets`).
- Open Graph и Twitter-карточки (превью в VK и Telegram).
- JSON-LD: Organization (главная, контакты), Person (специалисты), NewsArticle (новости), BreadcrumbList.
- `sitemap.xml` (статичные страницы плюс новости; новости добавляются при пересборке), `robots.txt` (закрыть служебные пути), RSS новостей.
- Единый канонический вариант домена (с `www` или без, кириллица или punycode) и 301 на него; HTTPS (Let's Encrypt в панели Beget - проверить, что включен и продлевается).
- Настоящие статусы: 404 для несуществующих страниц, 301-редиректы со старых адресов через `.htaccess`.
- Тестовая (staging) копия закрыта от индекса: `noindex` в мета-теге и заголовке, переключение переменной `SITE_ENV=staging|production`.
- Даты новостей на странице и в ленте только абсолютные (раздел 9, п. 15). В JSON-LD NewsArticle поля `datePublished` и `dateModified` (последнее берется из `edited_at`). Удаленная новость: страница отсутствует (404), записи нет в sitemap и RSS.
- Тема сайта - здоровье детей: для каждой статьи указывать автора-специалиста и дату обновления, давать ссылки на источники цифр (на старой главной "Минздрав России 2024", "Соцопрос 2023" без ссылок).
- Проверки в CI: у каждой страницы есть title, description, canonical и они не дублируются; в боевой сборке нет `noindex`; нет битых внутренних ссылок.
- Яндекс.Вебмастер и Google Search Console - полезны (подтверждение владения мета-тегом или DNS), счетчик Метрики для этого не нужен.

## 16. Критерии готовности

- На хостинге по расписанию раз в 2 часа запускается воркер. При новом, исправленном или удаленном посте в группе VK через 2-3 часа сайт отражает изменение без участия человека. Если изменений нет, сборка не запускается.
- При падении VK, воркера или сборки сайт продолжает открываться, ошибка видна в письме и `status.json`.
- Сборка не превышает суточный лимит CP (при `MAX_BUILDS_PER_DAY` по умолчанию).
- Правка текста поста дает пересборку, изменение только счетчиков лайков и просмотров - нет. Удаленный пост исчезает с сайта, а при сбое VK или ошибке токена посты не удаляются (письмо об ошибке приходит).
- Все даты новостей на сайте абсолютные, без относительных формулировок.
- Откат на предыдущий релиз выполняется сменой ссылки без пересборки.
- Все SEO-проверки CI проходят, тестовая копия закрыта от индекса, боевая нет.
- README для администратора хостинга готов, домен и автопродление проверены.
- Лог и `status.json` не содержат секретов, `.env` вне репозитория и вне публичной папки.
