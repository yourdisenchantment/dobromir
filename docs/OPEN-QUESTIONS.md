## Открыто

**О2 (2026-10-22): чем читать стену в будущем.** Проверка показала: ключ сообщества `wall.get`/`wall.getById` не может вовсе (ошибка 27), сервисный читает всю стену. Ключ сообщества годится только для событий о новых постах. Варианты:

1. **Оставить сервисный ключ навсегда** (рекомендация). Это ключ приложения, а не личный: доступа к аккаунту не дает, читает только открытое. Риск - удаление приложения или его блокировка; на этот случай - инструкция в README администратора.
2. **Ключ сообщества + Callback API.** VK сам присылает новые посты на адрес сайта. Нужен входящий адрес: на Beget это мог бы быть маленький PHP-приемник, пишущий события в файл (не демон). Но это отменяет решение «входящих эндпоинтов нет» (разд. 9 плана), правки и удаления старых постов этим путем не видны, а для истории все равно нужен сервисный ключ.
3. **Ключ сообщества + Long Poll** - невозможно: демоны на Beget запрещены.

**Решено 2026-10-23 (Павел): вариант 1, сервисный ключ насовсем.** Варианты 2 и 3 отклонены. Ключ сообщества воркеру не нужен; в настройках остается необязательным, на сервер его не класть.

**О9 (2026-10-24): как `.htaccess` попадает на сайт.** `public_html` - ссылка на релиз, релиз пересобирается, значит `.htaccess` должен оказываться в каждом релизе (или Apache должен читать его выше `public_html`, что зависит от настроек Beget). Шаблон - `deploy/htaccess.example`; его правила не зависят от `SITE_ENV` (боевой и тестовый сайт различаются по адресу), поэтому файл может быть один. Варианты:

1. **`site/public/.htaccess`** (рекомендация): Astro копирует `public/` в каждую сборку, файл версионируется вместе с сайтом, кода не нужно.
2. `release.py` копирует файл из `deploy/` в каждый релиз: лишний код ради того же результата.
3. `.htaccess` в папке сайта над `public_html`: без пересборок, но Apache может его не читать.

Сначала P1-7: читает ли Apache `.htaccess` в каталоге-ссылке, какие модули включены, отдает ли nginx Beget статику сам (тогда заголовки кэша для статики не сработают), как передается признак HTTPS. **Пока без ответа:** шаблон не подключен, сайт работает без `.htaccess`; 301 со старых адресов нужны только к переносу (P2-5).

- **Стили утверждены по стайлбуку** (Павел): «ничего необычного не заметил»; правки по стилям - ближе к концу работы, не сейчас.

На телефоне меню закрывается после выбора пункта.
- **Срок хранения новостей - N дней** (`NEWS_RETENTION_DAYS`, по умолчанию 30): на сайте и в базе только новости за этот срок, старше - удаляются вместе с фото. Отменяет «вся история стены» (план, разд. 6) и ограничивает мягкое удаление сроком. Нижнего порога («не меньше 12 последних») и исключения для старого закрепленного поста нет: в тихий месяц карусель может быть короче, старый закреп на сайт не попадает. Частота публикаций по разведке - около поста в день (30 дней - 26 постов, 40 фото).
- Следствия: проверка релиза - не «страниц стало меньше», а «у каждой новости из `news.json` есть страница»; чистка фото - не через 30 дней после последнего использования, а сразу, как только на фото не ссылается ни один пост, на свежем сайте; первичная загрузка (`backfill`) берет со стены только посты за срок.

## Решено 2026-10-23

- **Удаления замечаются и в окне** (Павел): снятый пост исчезает с сайта в пределах часа, а не ждет суточной сверки. Удален - сохраненный пост с датой не старше самого старого **обычного** поста окна, которого в окне нет; границу задают только обычные посты (закреп VK отдает первым, даже старый). Только по целому окну (набрано `VK_WINDOW` обычных постов или конец стены); пустое или неполное - «не знаем». Та же защита max(3, 20%). Посты старше окна по-прежнему проверяет суточная сверка. Код - `reconcile.window_missing`.
- **Интервал опроса VK - раз в час** (`17 * * * *`), было раз в 2 часа. Мгновенного получения постов нет и не будет: Long Poll - демон, Callback API - входящий адрес (оба отклонены в О2). Новый пост появляется на сайте в пределах часа плюс время сборки. Опрос без изменений дешевый (один `wall.get`), сборка только при изменениях и под `MAX_BUILDS_PER_DAY`. Пересмотреть после замера CP на хосте (P1-7): если дешево - чаще, если нет - реже.

Документы и видео не скачиваем и не храним - нерационально; на сайте показываем ссылкой на пост или вложение в VK, оформление - при дизайне карточки. Опросы не показываем: голосовать на сайте нельзя. В модели поста храним достаточно, чтобы построить ссылку (тип, `owner_id`, `id`, заголовок), без файлов.

- **2026-10-25, разведка боевой группы `dobromir.crimea`** (`survey --key service`, только чтение). 3076 постов с 19.02.2013 по 19.10.2026, 31 страница по 100 - **предел `count` 100 подтвержден**. **Поле `edited` есть** (519 постов). Закрепленный пост (4632) - первым в выдаче. 306 репостов, у 75 оригинал удален: VK помечает его полями `is_deleted`, `deleted_reason`, `deleted_details` - это **подтверждает допущение сверки P1-4** (пометка удаления у поста), хотя на самом `wall.getById` еще не проверено. Вложения: фото 5966, видео 501, аудио 81, документы 34, альбомы 6, ссылки 22, опрос 1. Разбор всех ответов - без ошибок; постов только с фото - 254 (запасной заголовок). Фото с репостами по длинной стороне выбранного размера: от 1600 px - 45%, 800-1599 - 39%, меньше 800 - 17%; высоких (высота больше двух ширин) - около 2%.
- **2026-10-25, P2-7. Разбор качает самый маленький размер фото, которого хватает на 1600 px**, а не самый большой: оригинал (`orig_photo`) бывает в несколько мегабайт, а хранится все равно копия до 1600 px. Если такого размера нет - самый большой. Средний выбранный размер на данных группы - 1,4 Мпикс.
- **2026-10-25, P2-7. Высокие картинки (плакаты, афиши) по правилу «длинная сторона».** Плакат 1000x3000 становится 533x1600 - мелкий текст на нем может читаться хуже. Пока оставлено как решено; пересмотреть по данным боевой группы (сколько там таких картинок): вариант - ограничивать высокие по ширине, а не по длинной стороне.
- **2026-10-25, P2-7. Пересчет старых JPEG ломает картинки в старых релизах.** После пересчета JPEG удаляется, а релизы, собранные раньше, ссылаются на него; откат на такой релиз покажет новости без фото. Касается только локальных данных тестовой группы: на сервере данных старого вида нет.
- **2026-10-25, P2-2. Чистка медиа - в воркере раз в сутки, только на свежем сайте.** Пока `pending` не снят, текущий релиз может еще показывать удаленный пост с его фото - чистка ждет удачной сборки. Отдельного задания cron нет: меньше писем и одна блокировка. Цена: откат на релиз старше 30 дней покажет удаленные тогда посты без картинок - откат нужен на часы, а не на месяц, поэтому принято.
- **2026-10-25, P2-2. Фото живого поста не удаляется при любой отметке.** Срок считается от `last_used_at`, но если экспорт перестанет отмечать фото (ошибка), через 30 дней ушли бы все картинки сайта; поэтому список «нужных сейчас» строится заново из живых постов, а такие случаи пишутся в лог предупреждением.
- **2026-10-24, P2-1. Копия базы - встроенным бэкапом SQLite из Python, не утилитой `sqlite3`.** Механизм тот же (`.backup` и `Connection.backup`), но утилиту на хосте никто не проверял, а Python там точно есть. Копия проверяется `PRAGMA integrity_check` до того, как получит свое имя; права 600 - в ней материалы о детях.
- **2026-10-24, P2-1. Имена за одну секунду.** Прогон скриптов показал: копии с суффиксом сортировались по строке раньше копии без него (`-1.sqlite` < `.sqlite`), а освобожденное чисткой имя занималось снова - новая копия выглядела старой и первой уходила в чистку. У релизов то же (`-10` раньше `-2`), а `rollback` сравнивал пути строками. Теперь порядок - по времени и номеру, номер за секунду всегда больше занятых; тесты на это есть. Больше одной сборки в секунду на деле не бывает, но чистка и откат опираются на этот порядок.
- **2026-10-24, P2-1. `deploy.sh` не держит блокировку воркера весь деплой**, ее берут только `migrate` и `build`: дочерние команды не смогли бы взять блокировку, которую держит родитель (`fcntl` - на процесс). Если cron запустит воркер посреди деплоя, худшее - письмо об ошибке, сайт остается на прежнем релизе; поэтому в справке - «не запускать около 17-й минуты».
- **2026-10-24, P2-1. Время cron на Beget считаем московским** (UTC+3, как `Europe/Simferopol`) - не проверено (P1-7). Копия базы стоит на 03:47, после суточной сверки.
- **2026-10-23, P1-6. Модуль `pipeline/release.py`, а не пакет `build/`.** Один модуль на сборку, проверки, переключение, чистку и откат; имя `build` к тому же путается с каталогами сборки. Команда отката - `python -m pipeline rollback [--to <релиз>]`, под той же блокировкой, что и воркер.
- **2026-10-23, P1-6. `public_html` - обычный каталог - воркер отказывается работать** (проверяется до сборки): это старый сайт, его первую замену на ссылку делает человек. Чистка трогает только каталоги с именем-временем (`20261023-101500`, при совпадении секунды - `-1`), текущий релиз не удаляется, даже если он старше пяти последних (после отката).
- **2026-10-23, P1-6. Окружение сборки собирается с нуля**, а не наследуется: `PATH`, `HOME`, `ASTRO_*`, `NEWS_JSON`, `SITE_URL`, `SITE_ENV`, мета-теги подтверждения. Ключи VK в процесс `npm` не попадают (тест). При сбое в лог пишутся последние 15 строк вывода сборки.
- **2026-10-23, P1-8. Фото в каркасе - обычный `<img src="/media/...">`, не `astro:assets`.** Решение плана (разд. 8) - показ через `astro:assets`. Но фото лежат вне проекта (`SITE_ROOT/media`), и читает ли их `astro:assets` - не проверено (открытый вопрос в AGENTS.md), а обработка тысяч фото на каждой сборке стоит CP. В каркасе - исходные файлы с `width`/`height` и `loading="lazy"`; выбор - при дизайне (P3) после замера CP (P1-7). Кнопки «скачать» пока нет.
- **2026-10-23, P1-8. Открытая графа и JSON-LD.** В каркасе только базовый Open Graph (тип, заголовок, описание, адрес); картинка превью, Twitter-карточки и JSON-LD (NewsArticle и др.) - в P3, при дизайне.
- **2026-10-23, P1-8. `no-undef` выключено для `.ts`** в `site/eslint.config.mjs`: правило не знает глобалов Node и веба (`process`, `URL`, `Response`), а необъявленные имена ловит `astro check`; так советует typescript-eslint.
- **2026-10-23, P1-5. Блокировка `fcntl.lockf` - между процессами.** Внутри одного процесса повторная блокировка того же файла проходит; поэтому тест «второй запуск при занятой блокировке» держит блокировку отдельным процессом, как в cron. Проверка в P1-7 на хосте - тоже двумя процессами (два окна SSH).
- **2026-10-23, P1-5. Время в `status.json` - местное** (Europe/Simferopol, с поясом): его читает администратор хостинга. При успехе воркер ничего не печатает - иначе cron присылал бы письмо каждый час.
- **2026-10-23, P1-4. «Пустой ответ - не удаление» - на уровне всей сверки, а не пачки.** BACKLOG: «пустой ответ целиком» не удаление. Если применять это к каждой пачке `getById` отдельно, посты, оказавшиеся в одной пачке (обычно самые старые, в последней неполной), не удалятся никогда - тест это показал. Выбрано: пустыми ответили **все** пачки - «не знаем»; иначе пустая пачка значит, что ее посты удалены. Случайный пустой ответ одной пачки ловит защита max(3, 20%). Правило - в `reconcile.classify_missing`.
- **2026-10-23, P1-4. Повод к сборке - изменился `news.json`.** Вместо отдельного учета «новый, измененный, удаленный, скачанное фото» - сравнение экспорта: счетчики его не меняют, правки, удаления, закреп и фото - меняют. Флаг `pending_since` хранится в базе и снимается только успешной сборкой (P1-6).
- **2026-10-23, P1-4. Пометка удаления у поста в ответе VK.** `is_deleted`/`deleted_reason` у поста в `getById` считается удалением - допущение, проверить на тестовой группе (удалить пост и запустить сверку).
- **2026-10-23, P1-3. Закреп - изменение, хотя в хэш не входит.** BACKLOG исключает закреп из хэша; но закреп меняет вид ленты, поэтому `Store.upsert` считает изменением смену хэша **или** закрепа. Хэш при этом остается без закрепа, как в BACKLOG.
- **2026-10-23, P1-3. Скачанное фото - тоже повод собрать сайт.** Фото, скачанное позже поста (сбой сети), меняет `news.json`, хотя пост не менялся. `download_photos` возвращает число скачанных, `write_news` - изменился ли файл; в P1-4 повод к сборке - любое из: изменения постов, скачанные фото, измененный файл.
- **2026-10-23, P1-3. В `posts` нет колонок `text` и `repost`** из списка BACKLOG: текст и репост всегда берутся разбором `raw_json`, отдельная копия разошлась бы с ним. Вместо `repost` - `repost_source` (имя источника из `extended=1`, которого в самом посте нет). Таблица `photos` хранит сам файл по id фото VK, а не пару «пост - фото»: какой пост какое фото использует, видно из `raw_json`.
- **2026-10-23, P1-2. Порядок вложений входит в хэш.** BACKLOG предлагал «отсортированный список идентификаторов вложений». Выбрано: порядок сохраняется - от него зависит, какое фото на обложке, то есть это видимое на сайте изменение. Цена: если VK когда-нибудь начнет отдавать вложения в другом порядке без правки поста, будет лишняя сборка (лимит сборок страхует). Вернуть сортировку - одна строка в `parse/hash.py` и тест `test_photo_order_changes_hash`.
- **2026-10-23, P1-2. Реклама отфильтрована.** Посты с `marked_as_ads` в новости не идут (BACKLOG: «рекламные пропускать»); в P1-2 поле проверялось только как флаг.
- **2026-10-23, P1-2. Владелец документа - пользователь, а не группа.** У `doc` в реальном ответе `owner_id` - id того, кто загрузил файл; страница документа в VK без ключа доступа, скорее всего, не откроется. Выбрано: модель хранит тип, id и заголовок, а ссылку сайт ведет на сам пост (`vk_url`). Проверить при верстке, открывается ли страница документа напрямую.
- **2026-10-23, P1-2. Посты без текста - пустой заголовок.** В тестовой группе 2 из 23 (только фото). Для фронтенда (P1-8): нужен запасной заголовок, например дата публикации.
- **2026-10-23, P1-2. Часовой пояс модели - `Europe/Simferopol` константой.** `LOCAL_TZ` берется из `settings.DEFAULT_TZ_NAME`, а не из `TZ_NAME` в настройках: модель не знает о настройках. Если `TZ_NAME` когда-нибудь поменяют, slug и даты в модели останутся по Симферополю. Свести в одно место при экспорте (P1-3).
- **2026-10-23, P1-2. Обезличенная фикстура реального ответа в репозитории.** `pipeline/tests/fixtures/wall_get_antarctic.json`: тестовая группа, детей нет; ссылки, ключи доступа, хэши, id и имена пользователей заменены (служебный id VK 100 оставлен). Правило «данные VK не в репозитории» относится к данным боевой группы; обезличенные фикстуры тестовой - исключение.

- **2026-10-22, решение Павла: на сервере uv с системным Python 3.10** (вместо `pip` + `requirements.txt`; варианты «pip» и «uv со своим Python» отклонены). Снимает риск `-e .` и сборки через `hatchling` из пункта ниже. Проверка на хосте - P1-7; до нее `requirements.txt` остается запасным путем.
- **2026-10-20, P0-1. `requirements.txt` начинается с `-e .`.** Команда из BACKLOG (`uv export --frozen --no-dev --no-hashes`) включает сам пакет как editable. Следствия для сервера: `pip install -r requirements.txt` работает только из каталога `pipeline/` и скачивает с PyPI сборщик `hatchling`. Выбрано: оставить как в BACKLOG (локально проверено, работает). Альтернатива, если на хосте не пойдет: `uv export ... --no-emit-project` и запуск воркера с `PYTHONPATH=pipeline/src`. Решить при P2-1 (`deploy.sh`) после P1-7.
- **2026-10-20, P0-1. glibc на хосте.** Колесо `pillow` 12.3.0 для Linux x86_64 - `manylinux_2_27/2_28`, нужна glibc >= 2.28. Хост: ядро 5.10, версия glibc не записана в отчете. Добавить в P1-7: `ldd --version | head -1`. Если ниже 2.28, pip попробует собирать pillow из исходников.
- **2026-10-20, P0-4. `SITE_ENV` без значения по умолчанию.** В BACKLOG умолчание не задано. Выбрано: обязательная переменная. Причина: умолчание `production` на тестовом сайте открывает его поисковикам, умолчание `staging` на боевом молча ставит `noindex` на год, пока разработчик недоступен. Громкая ошибка при запуске лучше. Отменить - одна строка в `settings.py` и тест.
- **2026-10-20, P0-4. Верхние границы `VK_PAGE_SIZE` и `VK_BY_ID_BATCH` = 100.** Для `wall.get` это известный предел `count`; для `wall.getById` - допущение (BACKLOG, таблица допущений). Значение больше 100 отклоняется при загрузке. Если P1-1 покажет другой предел, правится граница в `settings.py` и тест `test_bad_numbers`.
