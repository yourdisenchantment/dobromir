# Сервер: установка, обновление, ошибки

Для тех, у кого есть SSH-доступ к хостингу. Памятка для человека без технических знаний
(оплата, письма, `status.json`) - [README-for-hosting-admin.md](README-for-hosting-admin.md).

> На хосте еще не проверялось (BACKLOG, P1-7): доступ к GitVerse с хостинга, cron Beget,
> замена `public_html` ссылкой. Скрипты проверены тестами на временных репозиториях
> (`pipeline/tests/test_deploy.py`). Что окажется иначе - поправить здесь.

## Как устроено

```txt
у админа на компьютере                 GitVerse              сервер Beget
правка -> npm run build -> push  ---->  main  ---->  deploy.sh (cron :47 или руками)
                                                       git pull -> зависимости ->
                                                       пробная сборка -> база -> включить
                                        группа VK ---> run-worker.sh (cron :17): новости
```

- **Правки только у себя** и только через GitVerse: правки содержимого -
  `docs/HOWTO-add-content.md`, кода - `CONTRIBUTING.md`. В клоне на сервере ничего не
  правится: `deploy.sh` откажется обновляться, если там изменены файлы.
- **`deploy/deploy.sh`** забирает новое из `main` и выкладывает. Из cron раз в час
  (`--cron`, молчит, если нового нет) или руками - работает одинаково.
- **`deploy/run-worker.sh`** раз в час забирает новости из VK и пересобирает сайт, если
  они изменились. Обновление и воркер не идут одновременно: общая блокировка, второй
  ждет следующего запуска.
- **Сайт не ломается от ошибки.** Новая версия включается, только если собралась и
  прошла проверки; иначе сайт остается на прежнем релизе, а на почту приходит письмо.

Раскладка каталогов:

```txt
~/dobromir/                    клон репозитория (ветка main)
~/dobromir-data/               НЕ публичное: .env, db/, export/news.json, backup/,
                               logs/worker.log, logs/deploy.log, status.json, deploy-state
~/a978879k.beget.tech/
    public_html -> releases/<время>     ссылка на включенный релиз
    releases/                  последние 5 собранных версий сайта
    media/                     фото новостей
```

## Первая установка

1. **Доступ к GitVerse с сервера.** На сервере создать ключ только для чтения
   репозитория и добавить его в GitVerse (настройки репозитория, ключи развертывания;
   если их нет - ключ в профиле отдельного пользователя с правом чтения):

   ```bash
   ssh-keygen -t ed25519 -f ~/.ssh/gitverse -N "" -C "dobromir-server"
   cat ~/.ssh/gitverse.pub
   printf 'Host gitverse.ru\n  IdentityFile ~/.ssh/gitverse\n' >> ~/.ssh/config
   ```

2. **Клон** в домашний каталог:

   ```bash
   git clone git@gitverse.ru:yourdisenchantment/dobromir.git ~/dobromir
   ```

3. **Подготовка:** сначала проверка, потом выполнение. Скрипт создаст каталоги,
   `~/dobromir-data/.env` по образцу (права 600), поставит зависимости и соберет сайт
   на пробу; ничего не удаляет и `public_html` не трогает.

   ```bash
   cd ~/dobromir && ./deploy/bootstrap.sh && ./deploy/bootstrap.sh --apply
   ```

4. **Настройки:** в `~/dobromir-data/.env` вписать `SITE_ENV` (`production` или
   `staging`), `VK_SERVICE_TOKEN`, `VK_GROUP_ID`. Ключ никому не пересылать и в
   репозиторий не класть.
5. **Первый запуск воркера** - загрузит новости за срок хранения и соберет релиз:

   ```bash
   ./deploy/run-worker.sh
   ```

6. **Замена `public_html` ссылкой** - один раз, руками. Старый сайт не удалять, а
   переименовать: это и есть откат на старый сайт.

   ```bash
   cd ~/a978879k.beget.tech
   ls releases/                                  # имя последнего релиза
   mv public_html public_html.old-site
   ln -s releases/<имя> public_html
   ```

7. **Cron** - в панели Beget, раздел «CronTab», строки из `deploy/crontab.example`
   (воркер, обновление, копия базы). В поле почты - адреса всех, кто следит за сайтом.
8. **Проверка:** открыть сайт; через час - `~/dobromir-data/status.json`
   (`last_error: null`) и `~/dobromir-data/logs/deploy.log`.

## Обновить сайт

**Само:** cron раз в час, в 47 минут, запускает `deploy.sh --cron`. После `push` в
`main` сайт обновится в течение часа, на почту придет «Сайт обновлен: ...» со списком
вышедших коммитов.

**Руками**, не дожидаясь cron:

```bash
cd ~/dobromir && ./deploy/deploy.sh
```

Скрипт печатает ход работы, в конце - что вышло и как откатить. Ключи:

| Ключ | Когда |
|---|---|
| `--no-switch` | собрать и проверить, но не включать; включить потом командой, которую он напечатает |
| `--to <коммит>` | поставить код на определенный коммит (откат кода, см. ниже) |
| `--pip` | Python-зависимости через `pip`, если `uv` на хосте не работает |
| `--npm-ci` | переустановить зависимости сайта, даже если lock-файл не менялся |

Если в этот момент идет воркер, скрипт скажет «повторите через несколько минут».

**Выключить автообновление** - выключить задание `deploy.sh --cron` в панели «CronTab».
Обновлять тогда только руками.

## Письма и что делать

Письма приходят на адреса из поля почты в «CronTab». Подробности любой ошибки -
`~/dobromir-data/logs/deploy.log` (обновление) и `logs/worker.log` (новости).

| Письмо начинается с | Что случилось | Что делать |
|---|---|---|
| «Сайт обновлен: ...» | вышла новая версия | ничего; проверить сайт глазами |
| «Сайт не обновлен: ошибка на шаге «сборка»» | новая версия не собралась или не прошла проверки; сайт на прежнем релизе, код возвращен | причина - в «Последних строках журнала»; исправить у себя, `npm run build`, push. Этот коммит cron больше не пробует |
| «... «зависимости»», «... «Python-зависимости»» | не поставились пакеты (сеть, реестр) | повторить руками `./deploy/deploy.sh`; не проходит - смотреть журнал |
| «... «получение кода»» | сервер не достучался до GitVerse | проверить `ssh -T git@gitverse.ru` и ключ (шаг 1 установки) |
| «... «проверки»: в клоне на сервере изменены файлы» | кто-то правил файлы на сервере | `cd ~/dobromir && git status`, `git diff`: нужное перенести в репозиторий у себя, затем `git checkout -- .` на сервере |
| «... история ... переписали (force push)» | в GitVerse переписали историю `main` | разобраться в репозитории; поставить сервер на нужный коммит: `./deploy/deploy.sh --to <коммит>` |
| «... «миграции»» | новая схема базы не применилась; код оставлен новым, сайт на прежнем релизе | смотреть журнал; при необходимости «Восстановить базу» ниже |
| «... «включение релиза»» | релиз собран, но не включился | `ls -l ~/a978879k.beget.tech/public_html` - должна быть ссылка; включить руками (ниже) |
| письма воркера (ключ VK, «удаление остановлено», «сайт не пересобран») | новости | `README-for-hosting-admin.md`, раздел 4 |

## Откатить сайт

Без пересборки, за секунду - на предыдущий релиз или на любой из последних пяти:

```bash
cd ~/dobromir/pipeline
.venv/bin/python -m pipeline rollback               # на предыдущий
ls ~/a978879k.beget.tech/releases/                  # какие есть
.venv/bin/python -m pipeline rollback --to <имя>    # на названный
```

Следующее изменение новостей или кода соберет новый релиз из текущего кода - если
плохим был код, откатите и его.

## Откатить код

```bash
cd ~/dobromir && git log --oneline -10       # выбрать коммит
./deploy/deploy.sh --to <коммит>
```

Код встанет на этот коммит, сайт пересоберется на нем. **Автообновление при этом
ждет:** cron не трогает сервер, пока кто-нибудь не запустит `./deploy/deploy.sh` без
`--to` - тогда сервер вернется на свежий `main`. Правильное исправление - откатить
коммит в репозитории (`git revert`) у себя и сделать push.

## Восстановить базу из копии

Копии - `~/dobromir-data/backup/`, раз в сутки и перед каждой миграцией, 7 последних.

1. В «CronTab» выключить задания воркера и обновления.
2. Заменить базу копией, текущую сохранить рядом:

   ```bash
   cd ~/dobromir-data
   ls backup/                                   # выбрать копию
   mv db/dobromir.sqlite db/dobromir.sqlite.broken
   cp backup/<копия>.sqlite db/dobromir.sqlite
   ```

3. Если код новее копии - `cd ~/dobromir/pipeline && .venv/bin/python -m pipeline migrate`.
4. `~/dobromir/deploy/run-worker.sh` - доберет из VK то, чего нет в копии.
5. Включить задания cron обратно.

## Сменить ключ VK

1. Новый сервисный ключ - на dev.vk.com, в настройках приложения VK (сервисный ключ
   доступа). Ключ привязан к аккаунту владельца приложения.
2. Вписать в `~/dobromir-data/.env` строку `VK_SERVICE_TOKEN=...` вместо старой.
3. Проверить: `~/dobromir/deploy/run-worker.sh` - без вывода, `status.json` без ошибки.

## Новый админ

- **GitVerse:** добавить в участники репозитория - он правит у себя и делает push
  (`CONTRIBUTING.md`).
- **SSH на сервер** (если нужен): его публичный ключ - строкой в
  `~/.ssh/authorized_keys` на сервере. Пароль от панели Beget не раздавать.
- **Письма:** его адрес - в поле почты заданий «CronTab».

Ушел админ - убрать его ключ из `authorized_keys`, из участников GitVerse и адрес из
«CronTab».

## Чего не делать на сервере

- Не править файлы в `~/dobromir`: обновление откажется, пока правки не убраны.
- Не делать `git pull` руками: обновление - `./deploy/deploy.sh`, он и тянет, и
  проверяет, и откатывает.
- Не удалять `releases/` и `public_html.old-site`: это откат.
- Не трогать `bprof.a978879k.beget.tech` и не запускать ничего фоном (`nohup`, демоны):
  Beget это запрещает.
- Не показывать и не пересылать `~/dobromir-data/.env`.

## Настройка файла .env (добавлено 2026-11-02)

После клонирования и `./deploy/bootstrap.sh --apply` файл `~/dobromir-data/.env` заполняется так:

```txt
SITE_ROOT=/home/a/a978879k/a978879k.beget.tech
SITE_ENV=production
VK_SERVICE_TOKEN=<ваш_сервисный_ключ_VK>
VK_GROUP_ID=49938199
NEWS_RETENTION_DAYS=90
```

- Путь к `.env`: `~/dobromir-data/.env` (права 600). Другие файлы (например `~/.env.local`, `~/.env`) не читаются.
- Из перечисленного только `VK_SERVICE_TOKEN` вводится вручную (секрет, привязан к аккаунту владельца VK-приложения на dev.vk.com).
- `SITE_ENV`: `production` для реального сайта, `staging` для тестовой публикации (добавляет noindex).
- `VK_GROUP_ID` (без минуса) — id группы-источника новостей:
  - Боевая: `49938199` (vk.com/dobromir.crimea) — только production
  - Тестовая: `242263522` (vk.com/antarctic.test) — только локальные проверки
- `VK_COMMUNITY_TOKEN` оставить пустым: сервисный ключ читает стену полностью, ключ сообщества не требуется.
- `SITE_ROOT` — абсолютный путь (без `~`).
- `NEWS_RETENTION_DAYS` по умолчанию 90.
